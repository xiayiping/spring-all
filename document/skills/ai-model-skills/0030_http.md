
# Header

HTTP header words should be separated by '-' (dash), NOT '_' (underscore). Because dash is the http header standard.

HTTP header can NOT contain duplicated header keys, or nginx will block the request. (not disallowed by http standard).

# Response

The response should contain:

- meta: including non-business fields, like traceId
- data: a data as response of request
- error: an object adopting the [RFC9457](https://www.rfc-editor.org/rfc/rfc9457.html)
- Use standard http status [https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)
- for none json response like a octstream, the error response should obey the above rule.

An example of response:

```json
{
  "meta": {
    "traceId": "11118181ab12f1"
  },
  "data": {
    //....
  }
}
,
{
  "meta": {
    "traceId": "11118181ab12f1"
  },
  "error": {
    // RFC9457
  }
}

```

# Rest API

## Pagination

in Rest api, query by page, parameter should be :

- page: page number, indexed from 0
- pageSize: record per page.

## Sorting:

- sort.field
- sort.direction DESC/ASC (default ASC)

## Complex Search

It's always true to NOT use POST for query for below reason:

- the GET request for query is described by URL which can be shared and managed by browser history, so it can improve the user experience.
- so POST is purely always a creation action, no ambiguity.

url pattern : `/{resource}?query=xxxx`

search generic request body:

```json
{
  "filter": {
    "field1": {
      "gt": 100,
      "le": 400
    },
    "field2": {
      "startsWith": "uuu%"
    },
    "field3": {
      "eq": "abc"
    },
    "field5": {
      "in": [
        1,
        2,
        3,
        4,
        5
      ]
    },
    "field6": {
      "isNull": true
    }
  },
  "pagination": {
    "pageOffset": 0,
    "pageSize": 20
  },
  "sort": [
    {
      "field1": "ASC",
      "field2": "DESC"
    }
  ]
}
```

parse the json to text and pass to backend as urlencoded or base 64.

then the url pattern:  `items?query={json url encoded}`

In order not to add complexity, the conditions inside 'filter' linked with 'and'.

## Restful problems

In some case thinking an operation in restful way may be complicated. For example, 
a business check/approval flow for post an article.

The typical check/approval/confirm/.... for a record cannot simply be considered as
put/patch a whole resource or partial of resource attributes. By contrary, the operation
itself implicit some calculation logic, which should be processed in backend.

Comparing to normal put/patch, normally just modifying an attribute like user age, 
the age is already included in the request, but in approval/confirm, the requester doesn't know
how the resource will be look like after the operation. Then there's no way to provide the target
value of the resource in the request.

I called this kind of operation `shape changing of a resource`, comparing to `attribute changing` for normal
put/patch. In shape changing, the target value can't be decided until calculation is made by backend server.
